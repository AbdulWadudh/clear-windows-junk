# Building Clear Windows Junk.exe

No .NET SDK, no NuGet, no Visual Studio, no project file. The app compiles with
`csc.exe`, the C# compiler that ships inside Windows itself.

```
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe
```

That path exists on every stock Windows 10 and 11 install, because .NET Framework 4.x
is part of the OS. If you have Windows, you can already build this.

---

## Build it

```bat
app\build.cmd
```

Output lands next to the repo root as `Clear Windows Junk.exe` (~360 KB). That is the
whole deliverable — one file, no dependencies to ship with it.

Expected output:

```
Built G:\PROJECTS\clear-windows-junk\app\..\Clear Windows Junk.exe
```

Then verify:

```bat
"Clear Windows Junk.exe" --selftest
```

65 checks should pass and it exits `0`. A non-zero exit means a guard regressed — read
the failing line before shipping the binary.

---

## What the build script does

```bat
csc.exe /nologo /target:winexe /platform:anycpu /optimize+ /langversion:5 ^
        /win32icon:app.ico /out:"..\Clear Windows Junk.exe" ^
        /reference:System.dll System.Core.dll System.Management.dll ^
                   System.ServiceProcess.dll System.Xml.dll ^
                   PresentationFramework.dll PresentationCore.dll ^
                   WindowsBase.dll System.Xaml.dll ^
        AssemblyInfo.cs Theme.cs Core.cs Engine.cs Tree.cs Layout.cs Dialogs.cs Confirm.cs Ui.cs SelfTest.cs
```

Notes on the flags that are not obvious:

| Flag | Why |
|---|---|
| `/target:winexe` | No console window on launch. `--selftest` borrows the parent console via `AttachConsole` so its output is still visible from a shell. |
| `/langversion:5` | The bundled compiler is Roslyn-era but the Framework 4 targeting pack is C# 5. Keeps the source honest about what actually compiles — no interpolated strings, no `?.`, no expression-bodied members. |
| `/win32icon:app.ico` | Taskbar and Explorer icon. Regenerated by `make-icon.ps1` if missing. |
| WPF references | Pulled from `Framework64\v4.0.30319\WPF\`, not the GAC root. |

`build.cmd` regenerates `app.ico` automatically when it is absent, so a fresh clone
builds without extra steps.

## Source layout

Ten files, each with one job:

| File | Contains |
|---|---|
| `AssemblyInfo.cs` | The Win32 version resource — `AssemblyTitle` is the name Task Manager shows on the Processes tab. |
| `Theme.cs` | Colour and font tokens for light/dark, and the font pairings. Everything visual resolves through here. |
| `Core.cs` | Settings load/save (registry + portable file), Restart Manager interop, the close safety gate, and all filesystem work — measure, age-aware delete, single-path delete. |
| `Engine.cs` | The target list (what gets cleaned, and what each costs you), plus the scan and clean drivers. UI-free. |
| `Tree.cs` | Breakdown rows, the recursive child enumerator, and `PathCoverage` — the pure rule that stops a ticked child being counted twice. |
| `Layout.cs` | The whole window as a XAML string, kept out of the build system so `csc` alone is enough. |
| `Dialogs.cs` | The checkbox picker used for close / force / relaunch. |
| `Confirm.cs` | Themed confirm and notice dialogs, replacing `MessageBox.Show`. |
| `Ui.cs` | Wiring: selection maths, tri-state roll-up, the tree, threading, and `Program.Main`. |
| `SelfTest.cs` | The assertions. |

The engine has no reference to the UI. `Engine` talks to the front-end through
`IPrompter`, which is how the same clean logic can be driven by a window or, in the
PowerShell version, by a console.

## Editing the XAML

`Layout.cs` holds the window markup as a C# verbatim string. That is deliberate — a
`.xaml` file needs a build action and a project file, which would mean an SDK. The
string is parsed at runtime by `XamlReader.Parse`.

Two consequences worth knowing before you edit it:

**Quoting.** It is a `@"..."` verbatim string, so attributes use single quotes and any
literal `"` must be doubled.

**Order matters.** `StaticResource` only resolves against resources declared *earlier*
in the dictionary. The row templates sit at the end of `Border.Resources` because they
reference styles defined above them. Move them up and the app throws
`Cannot find resource named 'Eyebrow'` at startup. Use `DynamicResource` for anything
that changes with the theme.

A XAML mistake is a runtime exception, not a compile error — it surfaces as a startup
failure dialog with the full parse trace. Always launch once after editing `Layout.cs`.

## Changing what gets cleaned

Targets are declared in one list in `Engine.cs → BuildTargets()`:

```csharp
new Target {
    Name = "GPU / shader caches",
    Group = Grp.User,
    OnByDefault = true,
    Note = "rebuilt on next launch, first frames slower",
    Patterns = new[] { LA + @"\D3DSCache", LA + @"\NVIDIA\DXCache" }
},
```

| Field | Meaning |
|---|---|
| `Group` | `System` (needs admin), `User`, or `Advanced` (never on by default). |
| `OnByDefault` | Pre-ticked by "Safe defaults". |
| `Note` | The consequence, shown under the name and in the confirm dialog. Anything in `Advanced` should have one. |
| `Patterns` | Paths; one `*` segment is supported, e.g. `User Data\*\Cache`. |
| `NeedsAdmin` | Greys the row out and excludes it when unelevated. |
| `Pre` / `Post` | Run around the delete — used to stop and restart services. |
| `CustomClear` | Replaces the delete entirely, e.g. the DISM target. |
| `NoMeasure` | Size cannot be known up front; reports via the drive delta. |

Adding a target needs no other changes — the scan, the UI, the chart and the summary
all read from this list.

If the target can destroy something the user cares about, give it `Group = Advanced`
and a `Note`. That note is the only warning they get.

## Before you commit a change

```bat
app\build.cmd && "Clear Windows Junk.exe" --selftest
```

If you touched anything in `Core.cs` or `Tree.cs`, add an assertion to `SelfTest.cs`
for it. The existing ones exist because each of those behaviours was wrong at some
point:

* an old-looking folder taking a newly-written file with it
* measuring and deleting *through* a junction
* a partial folder being treated as if it covered everything under it
* a path being treated as covering itself
* the close gate accepting the terminal that launched the app

Verify a new assertion actually bites by breaking the code and watching it fail. A
test that passes against broken code is worse than no test — the PowerShell suite
silently passed for several revisions because `$ErrorActionPreference` was swallowing
`throw`.

## The PowerShell version

`Clear-WindowsJunk.ps1` needs no build step. It is standalone and shares the settings
file with the `.exe` when portable mode is on.

```powershell
.\Clear-WindowsJunk.ps1 -SelfTest
```

It is not generated from the C# sources, and the two are not kept in sync
automatically — a fix to a shared rule needs applying in both. `Core.cs` and the
helper functions near the top of the `.ps1` are the places that overlap.
